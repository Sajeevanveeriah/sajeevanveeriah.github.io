# Deployment-Guide

## Public browser edition

The public edition is generated by the portfolio repository and deployed through GitHub Pages. The deployment workflow must pass type checking, linting, static build, portfolio regression QA, OIA module QA, product QA, Lighthouse, export inventory and post-deployment live browser verification.

## Desktop edition

The desktop workflow runs on native GitHub-hosted Windows, macOS and Linux runners.

Outputs:

- Windows x64 NSIS installer
- Windows x64 portable executable
- macOS universal DMG
- macOS universal ZIP
- Linux x64 AppImage
- Linux x64 Debian package

Each artefact receives a SHA-256 manifest. A release-marked merge creates a GitHub prerelease containing all generated installers.

## Installation integrity

1. Download the product and matching SHA-256 manifest.
2. Calculate SHA-256 on the downloaded file.
3. Compare the complete digest.
4. Install only when the values match.
5. Keep the downloaded release manifest with the site handover evidence.

Unsigned community builds may trigger Windows SmartScreen or macOS Gatekeeper. Do not represent an unsigned build as organisation-signed.

## Production site deployment

A production site should deploy the UI, database, identity, historian and adapter services into explicit zones. The public static build must not be given direct uncontrolled access to field networks.

Minimum release evidence:

- approved requirements and design
- asset, I/O and network inventory
- software bill of materials
- dependency and container scans
- signed or checksummed release package
- environment comparison
- backup and restoration test
- role and permission test
- protocol and failure-mode tests
- FAT and SAT evidence
- rollback procedure
- commissioning and handover record

## Rollback

The Git tag, container digest, installer SHA-256, project-model version and database migration level form one rollback identity. A rollback is accepted only after the previous version is restored and its acceptance checks pass.
